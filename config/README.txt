DataRelay
=========

  1.87.0 でアプリ名を DataRelay にしました（旧: SymfoNavi Data Hub ／ その前: NaviToSQLite）。
  ローカル領域も %LOCALAPPDATA%\DataRelay\ へ移ります（起動時に自動で引き継ぎます）。
  この文書は1.66.x以降更新していません。以降の変更は、アプリ内の「バージョン情報 →
  更新履歴」で読めます。過去の項目に出てくる旧名は、当時の記録としてそのままにしてあります。

1.8.0 変更点:
- 日付・時刻の変数タグビルダーを刷新し、1か所で以下を組み合わせて1つのタグを作れるようにしました（要望1-①②③）:
  - ① 日付の対象: 現在日時 / 対象ファイル更新日 / 対象ファイル作成日
  - ② 日付の計算（新規・任意）: 基準日を年・月・日で前後へずらす（前(−)／後(+)）
  - ③ 使う部分と桁数: 年/月/日/時/分/秒を Y/M/D の数で桁指定（YYYYMMDD→20260726、YYYYMD→2026726）
- 日付の計算（要望1-③）を追加しました。ExcelのEDATE関数やVBAのDateAddのように、Nヶ月前・N年後・N日前後などを
  変数タグへ組み込めます。よく使う組み合わせ（前月・翌月・前年・翌年・前日・7日前・計算なし）をワンクリックで適用できます。
  月末を跨ぐ月・年の計算は、EDATE同様に月末へ丸めます（例: 1/31 の 1ヶ月後 → 2/28）。
- 生成されるタグへ日付計算を反映します（例: {now-1M:YYYYMM} ＝前月度、{rne_ctime+1Y:YYYYMMDD} ＝作成日の1年後）。
  命名パターンへ直接記入する場合も、対象名の直後へ +N/-N を並べて計算できます。
    単位: Y=年 / M=月 / W=週 / D=日 / H=時 / I=分 / S=秒。複数指定は年→月→週→日→時→分→秒の順で適用します。
  例: {now-1M:YYYYMM} / {rne_mtime-7D:YYYYMMDD} / {now+2Y-1M:YYYYMM00}
- プレビューは処理日時を基準に実ファイル名を即時試算します。対象と桁数の組み合わせ（要望1-①②）も、
  対象を切り替えても桁数・計算の設定を保持したまま、生成タグと実例を見ながら調整できます。
- 認知心理学(操作の統合・近接・即時フィードバック) / 情報アーキテクチャ(対象→計算→桁数の一貫した順序) /
  色彩調和(既存パレット踏襲・日付計算は補助色(暖色)で区別)。

1.6.0 変更点:
- 日付変数タグに「日付の対象」の選択を追加（要望1）:
  - 現在日時 / 対象ファイル更新日 / 対象ファイル作成日 の中から日付の取得元を選び、
    そのまま桁数（Y/M/D の数）の指定と組み合わせて1つのタグを生成できます。
  - 例: 対象ファイル更新日 + YYYYMD → {rne_mtime:YYYYMD} → 2026726。
    現在日時 + YYYYMMDD → {now:YYYYMMDD} → 20260726。
  - 対象ごとに別々だった日付専用タグ（RNE更新日・RNE作成日）を、このタグビルダーへ集約しました。
    専用タグの乱立をやめ、対象の切り替えと桁数調整を同じ場所で直感的に行えます。
  - 直接入力での桁数調整（YYYYMMDD→20260726、YYYYMD→2026726 のように Y/M/D の記号数が
    そのまま桁数）も従来どおり利用でき、生成タグの結果と一致します。
- 出力ファイル名の変数色分けを文字色のみへ変更（要望2）:
  - 一覧の変数由来部分の強調を、マーカー（背景色）から文字色のみの区別へ変更しました。
    変数バッジとの視覚的な衝突を解消しています。
- 認知心理学(操作の統合・近接・一貫性) / 情報アーキテクチャ(役割の一元化) / 色彩調和(強調手段の整理)。

1.5.0 変更点:
- 複数キュー処理の表示不具合を修正:

    「処理中 / 完了 / 失敗 / 待機」へ連動させました。進捗と件数が一致します。
  - 一覧の進捗表示で、完了したはずの対象が「順番待ち」コメントへ戻り、進捗バーの色が

    (queue_completed_ids / queue_failed_ids) を保持し、完了は緑のまま最後まで固定します。
- ファイル名の変数扱い判定を是正:
  - 変数欄へ文字を入力しただけ（例: SIKALOTDEF）では変数バッジを出さず、実際に {変数} が
    使われている場合のみ変数として扱います（既知トークンの実在で判定）。
  - 日付・時刻の変数タグを刷新しました。使う部分(年/月/日/時/分/秒)をONにして桁を選ぶだけで、
    Excelの書式設定のように Y/M/D の数で桁数が決まる分かりやすいタグへ変更しました。
    生成タグと実例をその場で確認できます（例: {now:YYYYMMDD}）。
  - 出力ファイル名の一覧・プレビューで、元が変数である部分に色を付けて識別できるようにしました。
- 用途コメント欄の追加:
  - 出力対象ごとに用途・メモを記録できるコメント欄(comment)を追加しました。
    一覧にも表示され、検索の対象になります。DBスキーマへ jobs.comment 列を後方互換で追加します。
- 認知心理学(状態の即時フィードバック・近接・一貫性) / 情報アーキテクチャ(役割別階層) /
  色彩調和(既存パレット踏襲・状態色の統一)。

起動:
  初回セットアップ（Pythonパッケージの導入確認）は start.bat で行ってください。
  日常の起動は start.vbs をダブルクリックしてください。コマンドプロンプトを表示せず、
  start_app.py（多重起動防止・app.pyのバックグラウンド起動・ブラウザーを開く処理）を実行します。
  2回目の起動では新規サーバーを起動せず、既存画面を開きます。

ブラウザーとアプリ稼働状態の同期:
  - スケジュール実行中にブラウザーを閉じよう（タブを閉じる・更新・ウィンドウを閉じるなど）とすると、
    ブラウザー標準の確認ダイアログが表示されます。
  - アプリ内の「アプリを終了」ボタンは、実行中は「中断して終了しますか？」の確認を行います。
    「はい」を選ぶと実行を中断し、以降の予約は開始せずにアプリを終了します。
    （直列実行中の1件はDDE/COM操作の途中では安全に打ち切れないため、安全な区切りまで進めてから停止します。
    　プロセス分離の並列実行（既定）は各ラインを即座に強制終了します。）
  - 逆にアプリ側（Python/Flask）が予期せず終了した場合は、画面に「サーバーとの接続が切れました」という
    通知が表示され、タブを閉じるよう案内します。
  - ハートビート監視（0.12.0／旧V36で誤検知を修正）:
    ・ブラウザーは10秒間隔でハートビートを送信します。送信はバックグラウンド抑制に強いWeb Workerで駆動し、
    　タブが再アクティブになった瞬間にも即時送信します。
    ・タブを切り替えて「非アクティブ」になっただけ（閉じていない）の状態は、閉じたとは判定しません。
    　バックグラウンドではタイマーが最悪1分に1回程度まで抑制されるため、無音のしきい値を200秒へ拡大しています。
    ・タブ×・ウィンドウ×・遷移など「実際に閉じる」ときだけ、明示クローズのビーコンを送信し、猶予（約12秒）後も
    　ハートビートが復帰しなければ実クローズと判断します。リロードやタブ切替では復帰したハートビートが判定を解除します。
    ・いずれの場合も、実行中のジョブが有る、または有効な自動実行スケジュールが有るときは終了しません（無人稼働を継続）。

起動できないときの調べ方（1.23.3）:
  - 起動画面に「起動確認がタイムアウトしました」とだけ出て原因が分からない場合、
    まず次のログを確認してください。
      %LOCALAPPDATA%\DataRelay\logs\app.log

  - ポートが使用中だった場合は、次の行が記録されます（1.23.3以降）。
      APP_PORT_IN_USE host=127.0.0.1 port=5031 ...
      APP_PORT_IN_USE_HINT 既にDataRelayが起動しているか、前回のプロセスが残っています。
    このときの対処:
      ① stop_app.bat を実行する
      ② それでも直らなければ、タスクマネージャーで python.exe / pythonw.exe を終了する
      ③ 起動し直す

  - 1.23.2以前は、ポートが空いていない場合にFlaskが自前で処理して標準出力へ出すだけだったため、
    app.log には何も残りませんでした。起動画面からは時間切れとしか見えず、原因が追えませんでした。

  - 起動時のその他の失敗は APP_RUN_FAILED として記録されます。

「調べる」が異常終了する不具合（1.23.2）:
  - 終了コード 3221226356（0xC0000374）は STATUS_HEAP_CORRUPTION、つまりヒープ破壊です。
    アクセス違反ではありませんでした。
  - 原因は、名前を受け取るバッファを番兵（0xFE）で埋めて渡していたことです。
    NUL文字が1つも無いため、DLLが文字列の長さを測ろうとするとバッファの外まで走査し、
    そのあとの書き込みでヒープを壊していました。
    1.21.1 まではゼロ埋めだったので長さが即座に0になり、この問題は起きていませんでした。
  - バッファをゼロ埋めに戻しました。大きさも1024バイトへ戻しています。

  - あわせて、列の判定に列名の読み取りを使わないようにしました。
    直近の出力ファイルの列名を渡し、NaviGetDataItem で引いて判定します。
    この経路はDLLから文字列を受け取らないため、名前の受け渡しに起因する事故が起きません。
  - それでも読み取りプロセスが落ちた場合は、名前の読み取りを止めて一度だけやり直します。
    件数と分割の判定は名前が無くても出せます。
  - 参照したアドレスの中身が名前として通らない（制御文字が混じる）場合は、空を返します。
    文字化けした名前を表示することはありません。

全体進捗バーの文字列の折り返し（1.23.2）:
  - 幅を広げ、表記を短くしました。
      「実行キュー全体 0 / 7 完了（実行中 6）」→「全体 0 / 7 完了 ・ 実行中 6」
    件数が3桁になっても1行に収まることを確認しています。

全体進捗バーが表示されない不具合（1.23.1）:
  - 割合の数値だけが出て、棒グラフが見えていませんでした。
    別のCSS指定（.queue-head>div）が詳細度で勝って横並びになり、棒の幅が0に潰れていたためです。
    ID指定で確実に縦積みになるよう直しました。棒は割合の数値のすぐ下に出ます。
  - 進捗バー用のクラス名が実行キューのバッジ（.cq-run）と重複していたので、別名にしました。

「調べる」でアプリごと停止する不具合（1.23.1）:
  - 原因は、DLLが返す文字列のアドレスを、読める範囲かどうか確かめずに参照していたことです。
    アクセス違反はPythonの例外にならないため、捕まえられずにプロセスが終了していました。
    ログに何も残らず「サーバーごと落ちた」ように見えるのはこのためです。
  - 対策を2段構えにしました。
      ① 参照する前に、実際に読める領域かどうかを確認する（WindowsではVirtualQuery）。
      　 読めない場合は参照せず空を返します。読む長さも領域内に収めます。
      ② RNEの読み取り自体を独立プロセスへ移す。DLL側で異常終了しても本体は生き残り、
      　 理由を画面に表示します。応答が無い場合も一定時間（既定180秒）で打ち切ります。
  - 通常の実行（抽出・出力・公開）には影響しません。以前から独立プロセスで動いています。

ログの末尾が下の帯に隠れる問題を直した（1.66.1）:

  【ログの末尾が、下の帯の下に隠れたままでした】

まとめて測る（ALL-IN）― 分け方と行の軸を同じ基準で比べ、速い順に並べる（1.57.0）:

  【分け方を一括で測れるようにしました】

行分割の下調べ（1.35.0）:
  - 列ではなく<行>を分けて同時に取れるかどうかを調べる機能です。
    対象を編集 → RNEを調べる →「行の分割可否を調べる」。
    実行も公開も行いません。既存の出力ファイルには触れません。

  - はじめに分かったこと: APIに「k行目からm行目」は無い。
    53関数を調べたところ、行を絞れそうなのは NaviDownLoadData だけですが、
    これは現在位置から前へ進むだけのカーソルで、開始位置の引数がありません。
    NaviGetRecordData は受信済みのデータを読む関数です。
    つまり「上から半分・下から半分」を、そのままの形で頼むことはできません。

  - しかし条件なら渡せます。しかも分割点は自動で見つけられます。
      NaviChangeConditionDI(hDItem, rc, condition, key, search, nonmatch, range,
                            lcheck, lvalue, rcheck, rvalue, reserve)
        … データ項目の集計条件。range / lvalue / rvalue があり、<範囲>で絞れます。
      NaviChangeConditionCP(hCPoint, rc, category, master, target)
        … 管理ポイントの条件。カテゴリ（値）を指定する形です。
    直近の出力ファイルを1回読めば、どの列をどこで区切ると行数が最も均等になるかは
    サーバーに触らずに分かります。人が分割点を決める必要はありません。

      データ項目（分割して取れる列）… 範囲で区切る。値の種類が多い列ほど正確に半分にできる
      管理ポイント（必ず残る列）  … カテゴリの組分け。値の種類が少ないと偏る
    偏りは「いちばん重い組が、均等だった場合の何倍か」で表します（1.00 が完全に均等）。

  - 数字だけの列は、数として並べて区切ります。

    ただしサーバー側が数として比べるか文字として比べるかは分からないため、

    転送は1バイトも発生しません。ここで得た時間が<サーバー側で結果を作る時間>で、
    通常の実行と保存の合計との差が<転送の時間>です。

    （ただし行は重複しないので、運ぶ量そのものは増えません。ここが列分割との大きな違いです）。

  - なぜ行分割に見込みがあるか（列分割との比較）:
      重複      … 行は重複しない。2分割なら各パートちょうど50%。列分割は68%止まりでした
      結合      … 行は縦に足すだけ。列分割の突き合わせは3.65〜5.54秒かかっていました
      サーバー側… 列を減らしても縮まなかった部分に、行を減らせば効く可能性があります
    合計で運ぶ量は、列2分割が153%（固定列が全パートに複製される）に対し、行2分割は100%です。
    回線の上限は合計側にあるため、<列分割と組み合わせると行分割単独より遅くなります>。

  - 行分割そのものはまだ実装していません。
    比較演算子（lcheck / rcheck）に渡す定数が未確認のためです。

分割なしと分割を競争させる（1.31.0）:
  - 分割なし1本と分割Nパートを<同時に>起動し、先に終わった方を採用して残りを中断する
    「競争」を追加しました。対象ごとに選べます（対象を編集 → RNEを調べる → 動作 → 競争させる）。
    影実行にも「競争させて測る」を追加しました（公開しない試し実行）。

  - 先に断っておきます。今のところ、競争は速さのためには働きません。
    競争させる2者が、まさにボトルネックそのもの（1本のVPN回線）を奪い合うためです。
    今日の実測から計算すると、こうなります。
      運ぶ量の合計 11.76 + 7.31 + 7.50 = 25.9MB を、上限 約1100 KB/s の回線へ同時に流す
      → 1本あたり約367 KB/s
      → パートの保存 15.4秒 → 約19.9秒、2分割の合計 37.4秒 → 約41.9秒
      → 勝つのは2分割の約41.9秒。分割せずに取る41.6秒と、ほぼ同じか少し遅い
    分割が稼いだ4.2秒を、増えた1本ぶんの帯域消費がそっくり食べてしまう計算です。
    サーバ側の問い合わせ実行も3本同時になるので、実際はもう少し悪くなるはずです。

  - それでも用意したのは、実測でしか分からないことがあるためです。
    上の計算は「3本が公平に帯域を分け合う」という仮定に立っています。
    影実行の「競争させて測る」で、実際に何秒で決着するかを確かめられます。

  - 競争が本当に効くのは、速さではなく<確実さ>です。
    分割が固まっても、分割なしが走り切れば公開できます。逆も同じです。
    「分割は速いことがあるが、たまに転ぶ」RNEでは、この保険に意味があります。

  - 決着の判定:
    ・分割なしが先に終わったら、その時点で決着。パートを中断します（結合も要りません）。
    ・パートが出そろったら、そこで分割なしを中断し、結合してから公開します。
      結合には実測で3〜6秒かかりますが、待たせません。パートが出そろった時点で
      分割なしはまだ大きく遅れているためです（負けた側だから遅れている）。
    ・両方こけたときだけ、分割なしでもう一度取り直します。

  - 競争は速さの裏付けを求めません。結果の一致さえ確認できていれば走ります
    （遅ければ競争に負けて捨てられるだけなので）。「自動」は従来どおり速さの裏付けも求めます。

  - 競争には分割なしのぶん1本余分にラインが要ります。2分割なら最低3本。
    持ち分（並列ライン数 ÷ 対象数）が足りなければ競争せず、これまで通りの判断で動きます。

  - 重要: 競争で測った値は、回線の見積もりにも速度比の平均にも使いません。
    奪い合いは、運ぶ量が多い分割なしの側をより強く痛めます。その結果、
    速度比はかえって<分割に有利へ>振れます。実測相当の値で計算すると、
      速度比   単独 1.11倍 → 競争 1.29倍
      伸びしろ 単独 1.44倍 → 競争 2.56倍（単一速度が奪い合いで沈むため）
    混ぜると「もっと分割せよ」という方向へ判断が狂います。記録には残しますが、
    集計からは除いています（split_trials の detail が 'race:' で始まる行）。

  - 主なログ:
      RACE_START  … 競争の開始（何本を同時に起こしたか）
      RACE_ORDER  … 全racerの着順と時刻。中断されたものには (中断) が付く
      RACE_WINNER … 勝者と所要時間。分割が勝った場合は結合の時間も内訳で出る
      SPLIT_TRIAL_RACE / SPLIT_TRIAL_RACE_ORDER … 影実行で競争させたとき

列分割を本番の実行へ組み込み（1.30.0）:
  - ここまで影実行（公開しない試し実行）でしか使えなかった列分割を、実際の出力ファイルの
    生成・公開でも使えるようにしました。

  - 実行時には何も測りません。ここが設計の要です。
    列ごとのデータ量を測るには出力ファイルを1回読む必要があり、11MBで約3秒かかります。
    分割で稼げるのが数秒なので、実行のたびに測っていたら、その場で得を使い切ってしまいます。
    そこで、影実行で「結果が一致し、かつ実際に速かった」と確認できた
    <どの列をどのパートが担当するか>そのものを保存し、実行時はそれを読むだけにしました。
    測り直しは影実行の側の仕事です。

  - 分割するのは、次の条件がすべてそろったときだけです。ひとつでも欠ければ1本で実行します。
      ① 対象の設定が「自動」または「常に分割」であること
      ② 保存済みの割り当てがあること（影実行で一致と、既定1.05倍以上の短縮を確認したもの）
      ③ RNEが当時から変わっていないこと
      ④ 列の顔ぶれが当時と同じであること（1列でも増減したら使いません）
      ⑤ 同じ名前の列が無いこと
      ⑥ 使えるラインが分割数ぶん空いていること
    分割しなかった場合は、その理由を SPLIT_RUN_SKIP としてログに残します。

  - 対象ごとに動作を選べます（対象を編集 → RNEを調べる → 本番の実行で列分割を使う）。
      自動      … 上の条件を満たしたときだけ分割（既定）
      常に分割  … 保存済みの割り当てが無ければその場で組み立てて分割（XLSXも対象）
      使わない  … 常に1本で実行
    同じ画面に「次に実行したらどうなるか」を表示します。分割しない場合は理由も出ます。

  - 同時プロセス数は、共通設定の並列ライン数を超えません。
    1対象あたりの持ち分＝並列ライン数 ÷ 対象数 で、これに収まる分割数だけを使います。
      例: ライン6本で対象1件 → 6本まで / 対象2件 → 3本まで / 対象6件以上 → 分割しない
    ログ: SPLIT_BUDGET configured_lines=6 jobs=1 per_job=6

  - 途中で失敗しても、出力ファイルが欠けることはありません。
    パートの実行や結合に失敗した場合は、分割なしで自動的に取り直してから公開します
    （ログ: SPLIT_RUN_FALLBACK）。時間はかかりますが、結果は必ず作られます。
    行集合が食い違った場合は、その割り当てを取り下げ、以後は使いません。

  - 分割で取得した回は、所要時間の基準（分割なし1本の実測）を上書きしません。
    判断の土台が分割後の値に置き換わると、次からの見積もりが狂うためです。

  - XLSXは、自動では分割しません。XLSXはAPIが直接書き出す方が速く、分割するとCSV経由＋
    結合＋変換になって前提が変わるためです。「常に分割」を選べば分割します。

  - 主なログ:
      SPLIT_PLAN_SAVE      … 影実行で裏付けの取れた割り当てを保存した
      SPLIT_PLAN_NOT_SAVED … 一致しなかった、または短縮が基準に届かなかった
      SPLIT_RUN_PLAN       … 本番で分割すると決めた（分割数・裏付け・結合キー数）
      SPLIT_RUN_SKIP       … 分割しなかった理由
      SPLIT_RUN_DONE       … 分割抽出と結合の内訳（最遅パートの実行・保存時間、合計転送量）
      SPLIT_RUN_FALLBACK   … 分割に失敗し、分割なしで取り直した
      SPLIT_PLAN_DROP      … 割り当てを取り下げた

分割の可否を回線の空きから判断（1.29.0）:
  - 列の割合が良くなったRNEの方が遅い、という結果になりました。理由は回線でした。
    これまでの影実行の実測値を並べると、はっきり出ています。
      1本 448 KB/s → 合計 794 KB/s（2本で1.77倍）
      1本 516 KB/s → 合計1099 KB/s（3本で2.13倍）
      1本 823 KB/s → 合計 974 KB/s（2本で1.18倍）  ← ほとんど伸びていない
    合計はどれも1100 KB/s あたりで頭打ちです。これが回線の上限とみられます。
    つまり分割で速くなるのは「1本では回線を使い切れていないとき」だけで、
    列の割合が良くても、1本ですでに上限近くまで出ていれば伸びしろがありません。

  - この考え方をそのまま判定に入れました。
      capacity … これまでに観測した合計スループットの最大値（回線の上限とみなす）
      base     … 直近の「分割なし」1本の速度
      伸びしろ  = capacity ÷ base
      速度倍率 σ(n) ≒ min(n, 伸びしろ)      有効な分割数 ≒ 伸びしろ（四捨五入）
    上の3件はすべてこの式で説明できます（1.77 / 2.13 / 1.18 に対し、伸びしろ 2.45 / 2.13 / 1.34）。

  - 分割数の推奨は、これで3つの軸から決まるようになりました。
      ① 列の割合    … 分割しても各パートに残ってしまう固定列の重さ
      ② 実測の証拠  … 影実行で得た速度倍率
      ③ データ量    … 1パートが小さすぎると効果が出ない（既定 2MB / 短縮5秒 が下限）
      ④ 回線の空き  … 今回追加。①〜③がどれだけ良くても、伸びしろ以上には速くなりません。

  - 「列の分割可否を調べる」の画面に、回線の状態を表示します。
    上限、いまの1本の速度、伸びしろ、そこから決まる有効な分割数が出ます。
    伸びしろが1.3倍程度しかないときは、分割せずそのまま実行する方が速い、という判断になります。
    回線が混んでいる時間帯なら同じRNEでも伸びしろが大きくなり、分割が効くようになります。
    判断は固定値ではなく、そのときの実測から毎回作り直します。

  - 「列の分割可否を調べる」がエラーになる不具合を2件直しました。
      ① 判定の内部でエラーになり「調査中にエラーが発生しました」となっていました。
      ② RNEを差し替えて列が増減した直後、まだ出力ファイルに無い列があると、
        重みの測定そのものが空を返し、「錨の列も立てられない」と誤って表示していました。
        出力ファイルに有る列だけで測るようにしました（不足分はログに COLUMN_WEIGHTS_PARTIAL）。

同名の列の検出（1.28.0）:
  - 同じ名前の列があるRNEでは、列分割を行いません。
    列分割は列名で担当を決め（担当外の列を名前で外す）、結合でも列名を突き合わせます。
    同名の列があると、外す対象を取り違えたり、結合で片方が黙って消えたりします。

  - 気づける場所を4つ用意しました。
      ① RNEの中身を調べる      … 重複している列名と回数を表示（通常の実行には影響しません）
      ② 列の分割可否を調べる    … 最上位の警告として表示し、分割不可と判定
      ③ 影実行の開始前          … 実行せずに中止（時間を無駄にしない）
      ④ 影実行の実行後          … RNEを差し替えて列が増えた場合に備え、実際の見出しで再確認
    ログ: COLUMN_DUPLICATES / SPLIT_TRIAL_DUPLICATES / SPLIT_TRIAL_DUPLICATES_ACTUAL

  - 結合処理そのものにも防御を入れました。
    パートの見出しや出力の列順に同名があれば、理由を明示して中止します。
    「結合後に同じ名前の列が残っています」も検出します。黙って片方の列が消えることはありません。

  - 対処: RNE側で列名を分ける（別名を付ける）と、分割できるようになります。

    パートを1本増やすたびに、セッション接続・カタログ読込・プロセス起動の固定費がかかります。
      設定キー split_min_part_mb        既定 2.0  … 1パートあたり最低このMB数を確保する
      設定キー split_min_gain_seconds   既定 5.0  … 実時間でこの秒数以上の得が無ければ分割しない
    例（転送60秒の対象）:
        1MB  → 1分割    3MB  → 1分割    6MB  → 2分割    12MB以上 → 4分割
        転送が4秒しかない対象 → 割合が良くても1分割（実時間の得が小さい）

分割の損益分岐（1.27.0）:
  - 並列にすると1本あたりの転送速度は落ちますが、合計は増えます。
    実測（SIKALOT.RNE）:
        1本  11.09MB / 21.99s = 516 KB/s   合計  516 KB/s
        2本   8.76MB / 22.56s = 398 KB/s   合計  796 KB/s（1.77倍）
        3本   8.00MB / 22.28s = 368 KB/s   合計 1103 KB/s（2.13倍）
    3分割は1本あたり72%のデータ量なのに、転送時間は分割なしとほぼ同じでした。

  - 損益分岐の式
        1パートが運ぶ割合   ratio(n) = f + (1-f)/n     f = 固定列の割合
        分割時の転送の所要  ∝ ratio(n) × n / σ(n)      σ(n) = 合計スループットの倍率
        σ(n) ≒ 1 + k(n-1) とすると、得になる条件は  f × n + (1-f) < σ(n)
        整理して                                      f < k
    分割数によらず、合計スループットの傾き k がそのまま分岐点になります。

  - kは影実行のたびに実測から学習します。各回は自分自身の「分割なし」を基準にします
    （回線が時間帯で変わるため、別の回の基準は使えません）。
  - 実測が無いうちは損益分岐を表示しません（推測で断定しないため）。
    影実行を1回行うと表示されるようになります。
  - ログ: SPLIT_THROUGHPUT（合計スループットの倍率・傾き・損益分岐）

  - RNE調整の目安（この環境の実測 k から）
        固定列 70% → 2分割で 1.02倍（損）
        固定列 55% → 2分割で 0.93倍
        固定列 40% → 2分割で 0.84倍
        固定列 20% → 2分割で 0.72倍
    ※これは転送部分だけの比です。全体の所要にはサーバ実行が含まれるため、
    　実際の短縮率はこれより小さくなります。

列分割の可否と効果の判定（1.24.0）:
  - 影実行で「分割間で行集合が一致しません」となる場合、原因は結合ではありません。
    **データ項目を外すと、返ってくる行そのものが変わる**問い合わせだからです。
    実測例（SIKALOT.RNE）:
        分割なし   14445行 / 177列
        パート1/2  14443行 / 143列
        パート2/2   2144行 / 143列   ← 行数が桁違い
    この場合、どう結合しても正しい結果にはなりません。中止するのが正解です。
  - 一度この食い違いが確認されたRNEは、以後は分割対象から外します。
    同じ試行を繰り返しません（再試行したい場合は影実行を強制指定してください）。

  - 効果の見積もりを、実測の内訳に基づく式へ改めました。
    分割で縮むのは「結果の転送」だけです。サーバ側の問い合わせ実行は行数で決まるため、
    列を減らしても縮まず、しかも**各パートが満額払います**。
    実測例（SIKALOT.RNE / 1回104.6秒）:
        サーバ実行  60.4秒（58%）… 分割しても縮まない。各パートが満額払う
        転送・保存  31.7秒（30%）… ここだけが列の割合に応じて縮む
        2分割にしても 98.5秒（短縮6%）、転送をゼロにしても 72.9秒（短縮30%）が下限
    以前の見積もり（2分割で0.46倍）は、この点を織り込んでおらず過大でした。

  - 通常実行のたびに実行時間の内訳をRNE単位で記録し、
    「分割しても何%変わるか」を影実行の前に表示します。無駄な待ち時間を避けるためです。
  - 見込みの差が1割未満のときは分割を勧めません。
    同じ問い合わせを何本も走らせる価値がないためです。

    実測は影実行のたびに記録され、同じRNEの次回の判断に使われます。

  - 条件節の見直しでデータ項目が増えれば、分割できる列も増えます。RNEを更新すると

  - x64のDLLはあるのに読み込めない場合、多くは 64bit版のVisual C++ 再頒布可能パッケージ
    （2015-2022 x64）が未インストールです。SymfoNaviクライアントは32bitのため、
    クライアントを入れても64bit側のランタイムは入りません。
        https://aka.ms/vs/17/release/vc_redist.x64.exe
  - 上記を入れられない場合は、32bit版のPythonを使う方法もあります。
    その場合は C:\NAVIAP\dllVC14 （32bit）が使われ、32bit側のランタイムだけで動作します。

別のPCへ配置したときの起動エラー（1.20.6）:
  - 「必要なPythonパッケージが不足しています / requirements.txt が見つかりません」が出る場合、
    1.20.6 以降へ更新してください（start.vbs の探し先の修正が入っています）。
  - requirements.txt は config フォルダーにあります。アプリ直下にはありません。
  - 起動時のパッケージ確認は、不足しているPCでのみ実行されます。必要なパッケージが既に入っている
    PCではこの処理に到達しないため、同じ構成でも一方でだけエラーが出ることがあります。
  - 1.20.7 以降、起動に必須なのは Flask だけです。他の3つが無くても起動します
    （不足している機能を使ったときに初めてエラーになります）。
      API方式でのSQLite3/CSV/TXT出力 … pywin32・xlrd は不要です
      通知領域のアイコン             … pywin32 が必要（無い場合はアイコンなしで動作）
      XLSX出力・ビュワーのXLSX表示   … openpyxl が必要
      ACCDB出力                      … pywin32 が必要
      DDE方式での抽出                … pywin32(win32ui, dde) と xlrd が必要
    社内プロキシ等でpipが使えない環境（407認証エラーなど）でも、まず起動できます。
  - 必要なパッケージは次の4つだけです（全ソースのimportから確認済み）。
        Flask     … 画面・API（app.py）
        pywin32   … win32ui / dde / win32com / pythoncom / win32gui など（app.py, tray_icon.py）
        xlrd      … XLS読み込み（app.py）
        openpyxl  … XLSX読み書き（app.py）
  - pip の実行に失敗する場合（社内プロキシ・オフラインなど）は、手動で導入してください:
        pip install --user Flask pywin32 xlrd openpyxl
  - pywin32 を入れても win32ui / dde だけ読み込めない場合は、後処理が必要です:
        python -m pywin32_postinstall -install
    （win32ui と dde は site-packages\pythonwin\ に入るため、win32api だけ成功して
      この2つが失敗することがあります。不足表示が win32ui / dde のときはこれを試してください）
  - 1.20.6 以降は、エラー画面に「不足: 」として不足しているパッケージ名が表示されます。
  - どのパスを使ったかは logs\vbs_launcher.log の REQUIREMENTS 行で確認できます。

並列実行の起動順と起動間隔（1.20.5）:
  - 重い対象から先に流します。バッチ全体の所要は一番重い対象で決まるため、それが後ろに回ると
    その分だけ全体が延びます。規模は前回実績の 行数×列数 を目安にします。
    実績が無い対象は大きさが読めないため先に流します。ログの BATCH_ORDER で順序を確認できます。
  - ラインの起動を少しずつずらします。一斉に起動するとNavigator APIのセッション接続が競合し、
    1本あたりの接続時間が数倍に伸びるためです（実測: 単独 約1.0秒 / 6本同時 2.3〜7.2秒）。
  - 設定 → 抽出方式 → 並列処理 →「ライン起動の間隔」（既定700ミリ秒、0で従来どおり一斉起動）。
  - 効果は実行後のログの JOB_PROFILE の api_open_session で確認できます。

自動実行の取りこぼし対策（1.20.4）:
  - 時刻を指定した予定（毎日・曜日・毎月・特定日）は、その時刻ちょうどの1分間に別の処理が
    実行中だと、その日は一度も実行されませんでした。スケジューラーは他の処理の実行中は
    判定をスキップするためです。
  - 設定 → 安全性とバックアップ → 「自動実行の取りこぼし対策」で猶予時間を指定できます（既定30分）。
    予定時刻から猶予時間内であれば、手が空いた時点で遅れて実行します。
  - 猶予中に何度判定しても発火は1日1回です。日をまたぐ猶予は行いません
    （翌日に前日ぶんが走ることはありません）。
  - 0分にすると従来どおり予定時刻の1分間だけを見ます。
  - 「N分ごと」の間隔指定は対象外です（次の区切りで発火するため影響がありません）。

処理速度を調べるためのログ項目（1.20.1）:
  - 全ログ行の先頭に [pid NNNN] が入ります。並列実行では複数プロセスが同じログへ書くため、
    pidで絞り込むとライン1本ぶんの流れだけを追えます。
  - RUN_ENVIRONMENT … 実行開始時に1回。この端末が遅いのかどうかの判断材料。
      cpu=              CPUコア数
      mem_load=         メモリ使用率（Windowsのみ）
      mem_avail_mb=     空きメモリ
      work_write_mb_s=  中間CSVの書き出し先の実測書き込み速度。極端に低い日はディスク側が原因。
      rne_scan_ms=      RNE置き場（BOX等）の応答時間。起動が遅い日はここが伸びます。
  - WORKER_READY … ワーカー1本の起動代。
      spawn_to_import=  Python起動＋app.py読込。BOX上のため環境により数秒かかることがあります。
      import_to_job=    読込完了から抽出開始まで。
  - JOB_PROFILE … 対象1件の工程内訳を1行に集約。時間の長い順に並びます。
      api_open_session=   Navigator APIのセッション接続。複数ラインが同時に接続すると伸びます
                          （実測: 6ライン同時=約4.4〜5.4秒 / 単独=約1.0秒）。
      api_execute_catalog= サーバー側の問い合わせ実行。RNEの内容とサーバー負荷で決まります。
      api_save_csv=       APIのCSV書き出し。列構成によって速度が10倍近く変わります。
      pending_apply=      更新保留ファイルの確認・適用。公開先がネットワーク共有の場合、
                          並列ライン数だけ同時にフォルダーを列挙するため待ちが出ることがあります。
      job_preflight=      出力先・RNEの確認。
      other=              内訳に入らなかった時間。ここが大きい場合はご連絡ください。
  - PENDING_SCAN … 更新保留ファイルを探すための公開先フォルダーの列挙。
      matched=            見つかった保留ファイルの件数（通常は0）。
      elapsed=            列挙にかかった時間。共有が重いとここが伸びます。
      例: total=271.86s api_save_csv=243.49s(89.6%) api_execute_catalog=23.47s(8.6%) ...
      どの工程が支配的かが一目で分かります。
  - STEP_END phase=api_save_csv の throughput_kb_s / ms_per_row … CSV書き出しの実効速度。
  - STEP_END phase=api_execute_catalog の rows_per_sec … サーバー側の応答速度。
  - 速度についてご相談いただく際は、ログ画面の「要約コピー」をお使いください。
    上記の計測行はすべて要約に含まれます。

API抽出は常に独立プロセスで実行（1.20.0）:
  - API方式の抽出は、対象が1件でも、並列ライン数が1でも、必ず独立したプロセスで実行します。
  - 理由: アプリ内で直接DLLを呼ぶ経路ではAPIのCSV書き出しが約45KB/sしか出ず、独立プロセス経由の
    0.5〜4MB/sに対して一桁以上遅くなっていたためです。重い抽出ほど差が大きく開きます。
    （実測: 14,357件×177列で、書き出しだけに243秒。独立プロセス経由なら約23秒の見込み）
  - 対象が1件のときも、実行状況は「ライン 1」として並列実行と同じ表示になります。
  - 抽出ログの api_save_csv に throughput_kb_s（実効速度）と ms_per_row（1行あたりの時間）を出力します。
    処理が遅いと感じたときは、この2つを他の実行と見比べてください。
  - 対象1件あたり2〜5秒のセッション接続が必要になるため、極端に小さいジョブを多数まとめて実行する場合は
    その分の時間が加算されます。書き出しの短縮幅の方が大きいため、通常は全体として速くなります。

通知領域への常駐（1.19.0）:
  - タブを閉じたとき、次のいずれかに該当する場合はアプリを終了せず、通知領域（タスクバー右側）へ常駐します。
      ・処理を実行中
      ・実行キューに待機中の指令がある
      ・有効な自動実行スケジュールがある
    常駐へ切り替わる際に、通知（バルーン）でお知らせします。
  - 常駐中の通知領域アイコンでできること:
      ・ダブルクリック          … 画面を開く
      ・右クリック → 画面を開く … 画面を開く
      ・右クリック → アプリを終了 … アプリを完全に終了する
      ・右クリックメニューの中段に、現在の状態（実行中／予定あり／キュー待機）を表示します。

  - 予定もキューも無く待機中の場合は、これまでどおりタブを閉じると自動的に終了します。
  - 通知領域の常駐はWindowsでのみ動作します（pywin32を使用。追加パッケージは不要）。
    利用できない環境では、常駐アイコンなしで従来どおり動作します（アプリは止まりません）。

公開ファイルの更新方式:

抽出期間（動的日付）: 1.7.0
- RNEに定義済みの時間型管理ポイントへ、実行時の処理日時を基準にした相対期間を実行直前に適用します。
- RNE本体やカラム（使用するデータ項目）の指定は変更しません。期間だけをメモリ上で差し替えてから実行し、
  RNEは元のまま保持します（定期実行での日付更新に最適）。
- 使用API: Navigator API の NaviChangePeriod。対象の時間型管理ポイントは、
  管理ポイント名を指定した場合は 条件→表側→表頭 の順に探索、未指定時は
  時間フィールドの時間型管理ポイント（NaviGetControlPointForTimeSpan）を自動選択します。
- 設定は対象ファイル設定モーダルの「基本・入出力」タブ内「抽出期間（動的日付）」で行います。
  ・期間の単位: 月度（YYYYMM00 / NAVI_MONTH）または 年月日（YYYYMMDD / NAVI_YMD）
  ・開始期(S)・終了期(E): 当月／当日を基準に、前後Nを指定（SymfoNaviの相対指定と同じ考え方）
  ・よく使う組み合わせ: 今月度／前月度／前月〜今月／当日／前日／過去7日／前日〜当日 をワンクリック適用
  ・対象の時間管理ポイント: 空欄で自動、または「候補を取得」でRNE内の時間型を自動検出して選択
- プレビューは処理日時を基準に実際の抽出範囲を即時表示します（例: 2026年6月度 ～ 2026年7月度）。
- 期間が有効なジョブでは実行ログに STEP phase=api_change_period と DYNAMIC_PERIOD を記録し、
  適用した単位・開始終了(YYYYMMDD/YYYYMM00)・対象管理ポイントを後から追跡できます。
- 注意: 相対期間が有効なのに時間型管理ポイントの特定や期間適用に失敗した場合は、
  誤った期間での公開を避けるためジョブを失敗として扱います（RNEの設定で全期間抽出することはしません）。
- DDE互換方式では本機能は適用されません（Navigator API方式で使用してください）。
- 候補の自動検出は NaviGetControlPointNumber / NaviGetControlPoint2 / NaviGetControlPointType /
  NaviGetNameCP を使用します。DLLがこれらを公開していない環境では手入力または自動選択で動作します。
