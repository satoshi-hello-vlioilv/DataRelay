1.8.0 変更点:
- 日付・時刻の変数タグビルダーを刷新し、1か所で以下を組み合わせて1つのタグを作れるようにしました（要望1-①②③）:
  - ① 日付の対象: 現在日時 / 対象ファイル更新日 / 対象ファイル作成日
  - ② 日付の計算（新規・任意）: 基準日を年・月・日で前後へずらす（前(−)／後(+)）
  - ③ 使う部分と桁数: 年/月/日/時/分/秒を Y/M/D の数で桁指定（YYYYMMDD→20260726、YYYYMD→2026726）
- 日付の計算（要望1-③）を追加しました。ExcelのEDATE関数やVBAのDateAddのように、Nヶ月前・N年後・N日前後などを
  変数タグへ組み込めます。よく使う組み合わせ（前月・翌月・前年・翌年・前日・7日前・計算なし）をワンクリックで適用できます。
  月末を跨ぐ月・年の計算は、EDATE同様に月末へ丸めます（例: 1/31 の 1ヶ月後 → 2/28）。
- 生成されるタグへ日付計算を反映します（例: {now-1M:YYYYMM} ＝前月度、{rne_ctime+1Y:YYYYMMDD} ＝作成日の1年後）。
  命名パターンへ直接記入する場合も、対象名の直後へ +N/-N を並べて計算できます。
    単位: Y=年 / M=月 / W=週 / D=日 / H=時 / I=分 / S=秒。複数指定は年→月→週→日→時→分→秒の順で適用します。
  例: {now-1M:YYYYMM} / {rne_mtime-7D:YYYYMMDD} / {now+2Y-1M:YYYYMM00}
- プレビューは処理日時を基準に実ファイル名を即時試算します。対象と桁数の組み合わせ（要望1-①②）も、
  対象を切り替えても桁数・計算の設定を保持したまま、生成タグと実例を見ながら調整できます。
- 認知心理学(操作の統合・近接・即時フィードバック) / 情報アーキテクチャ(対象→計算→桁数の一貫した順序) /
  色彩調和(既存パレット踏襲・日付計算は補助色(暖色)で区別)。

起動:
  初回セットアップ（Pythonパッケージの導入確認）は start.bat で行ってください。
  日常の起動は start.vbs をダブルクリックしてください。コマンドプロンプトを表示せず、
  start_app.py（多重起動防止・app.pyのバックグラウンド起動・ブラウザーを開く処理）を実行します。
  2回目の起動では新規サーバーを起動せず、既存画面を開きます。

ブラウザーとアプリ稼働状態の同期:
  - スケジュール実行中にブラウザーを閉じよう（タブを閉じる・更新・ウィンドウを閉じるなど）とすると、
    ブラウザー標準の確認ダイアログが表示されます。
  - アプリ内の「アプリを終了」ボタンは、実行中は「中断して終了しますか？」の確認を行います。
    「はい」を選ぶと実行を中断し、以降の予約は開始せずにアプリを終了します。
    （直列実行中の1件はDDE/COM操作の途中では安全に打ち切れないため、安全な区切りまで進めてから停止します。
    　プロセス分離の並列実行（既定）は各ラインを即座に強制終了します。）
  - 逆にアプリ側（Python/Flask）が予期せず終了した場合は、画面に「サーバーとの接続が切れました」という
    通知が表示され、タブを閉じるよう案内します。
  - ハートビート監視（0.12.0／旧V36で誤検知を修正）:
    ・ブラウザーは10秒間隔でハートビートを送信します。送信はバックグラウンド抑制に強いWeb Workerで駆動し、
    　タブが再アクティブになった瞬間にも即時送信します。
    ・タブを切り替えて「非アクティブ」になっただけ（閉じていない）の状態は、閉じたとは判定しません。
    　バックグラウンドではタイマーが最悪1分に1回程度まで抑制されるため、無音のしきい値を200秒へ拡大しています。
    ・タブ×・ウィンドウ×・遷移など「実際に閉じる」ときだけ、明示クローズのビーコンを送信し、猶予（約12秒）後も
    　ハートビートが復帰しなければ実クローズと判断します。リロードやタブ切替では復帰したハートビートが判定を解除します。
    ・いずれの場合も、実行中のジョブが有る、または有効な自動実行スケジュールが有るときは終了しません（無人稼働を継続）。

自動実行の取りこぼし対策（1.20.4）:
  - 時刻を指定した予定（毎日・曜日・毎月・特定日）は、その時刻ちょうどの1分間に別の処理が
    実行中だと、その日は一度も実行されませんでした。スケジューラーは他の処理の実行中は
    判定をスキップするためです。
  - 設定 → 安全性とバックアップ → 「自動実行の取りこぼし対策」で猶予時間を指定できます（既定30分）。
    予定時刻から猶予時間内であれば、手が空いた時点で遅れて実行します。
  - 猶予中に何度判定しても発火は1日1回です。日をまたぐ猶予は行いません
    （翌日に前日ぶんが走ることはありません）。
  - 0分にすると従来どおり予定時刻の1分間だけを見ます。
  - 「N分ごと」の間隔指定は対象外です（次の区切りで発火するため影響がありません）。

処理速度を調べるためのログ項目（1.20.1）:
  - 全ログ行の先頭に [pid NNNN] が入ります。並列実行では複数プロセスが同じログへ書くため、
    pidで絞り込むとライン1本ぶんの流れだけを追えます。
  - RUN_ENVIRONMENT … 実行開始時に1回。この端末が遅いのかどうかの判断材料。
      cpu=              CPUコア数
      mem_load=         メモリ使用率（Windowsのみ）
      mem_avail_mb=     空きメモリ
      work_write_mb_s=  中間CSVの書き出し先の実測書き込み速度。極端に低い日はディスク側が原因。
      rne_scan_ms=      RNE置き場（BOX等）の応答時間。起動が遅い日はここが伸びます。
  - WORKER_READY … ワーカー1本の起動代。
      spawn_to_import=  Python起動＋app.py読込。BOX上のため環境により数秒かかることがあります。
      import_to_job=    読込完了から抽出開始まで。
  - JOB_PROFILE … 対象1件の工程内訳を1行に集約。時間の長い順に並びます。
      api_open_session=   Navigator APIのセッション接続。複数ラインが同時に接続すると伸びます
                          （実測: 6ライン同時=約4.4〜5.4秒 / 単独=約1.0秒）。
      api_execute_catalog= サーバー側の問い合わせ実行。RNEの内容とサーバー負荷で決まります。
      api_save_csv=       APIのCSV書き出し。列構成によって速度が10倍近く変わります。
      pending_apply=      更新保留ファイルの確認・適用。公開先がネットワーク共有の場合、
                          並列ライン数だけ同時にフォルダーを列挙するため待ちが出ることがあります。
      job_preflight=      出力先・RNEの確認。
      other=              内訳に入らなかった時間。ここが大きい場合はご連絡ください。
  - PENDING_SCAN … 更新保留ファイルを探すための公開先フォルダーの列挙。
      matched=            見つかった保留ファイルの件数（通常は0）。
      elapsed=            列挙にかかった時間。共有が重いとここが伸びます。
      例: total=271.86s api_save_csv=243.49s(89.6%) api_execute_catalog=23.47s(8.6%) ...
      どの工程が支配的かが一目で分かります。
  - STEP_END phase=api_save_csv の throughput_kb_s / ms_per_row … CSV書き出しの実効速度。
  - STEP_END phase=api_execute_catalog の rows_per_sec … サーバー側の応答速度。
  - 速度についてご相談いただく際は、ログ画面の「要約コピー」をお使いください。
    上記の計測行はすべて要約に含まれます。

API抽出は常に独立プロセスで実行（1.20.0）:
  - API方式の抽出は、対象が1件でも、並列ライン数が1でも、必ず独立したプロセスで実行します。
  - 理由: アプリ内で直接DLLを呼ぶ経路ではAPIのCSV書き出しが約45KB/sしか出ず、独立プロセス経由の
    0.5〜4MB/sに対して一桁以上遅くなっていたためです。重い抽出ほど差が大きく開きます。
    （実測: 14,357件×177列で、書き出しだけに243秒。独立プロセス経由なら約23秒の見込み）
  - 対象が1件のときも、実行状況は「ライン 1」として並列実行と同じ表示になります。
  - 抽出ログの api_save_csv に throughput_kb_s（実効速度）と ms_per_row（1行あたりの時間）を出力します。
    処理が遅いと感じたときは、この2つを他の実行と見比べてください。
  - 対象1件あたり2〜5秒のセッション接続が必要になるため、極端に小さいジョブを多数まとめて実行する場合は
    その分の時間が加算されます。書き出しの短縮幅の方が大きいため、通常は全体として速くなります。

公開ファイルの更新方式:
  1. SymfoNaviの中間XLSはローカル一時フォルダーへ作成

  4. 3秒以内で原子的な置換を実行
  5. 他PCで開かれていて置換不能なら待ち続けず、同じ公開先に
     ファイル名.pending_YYYYMMDD_HHMMSS.拡張子 として新しい正しいファイルを保存

抽出期間（動的日付）: 1.7.0
- RNEに定義済みの時間型管理ポイントへ、実行時の処理日時を基準にした相対期間を実行直前に適用します。
- RNE本体やカラム（使用するデータ項目）の指定は変更しません。期間だけをメモリ上で差し替えてから実行し、
  RNEは元のまま保持します（定期実行での日付更新に最適）。
- 使用API: Navigator API の NaviChangePeriod。対象の時間型管理ポイントは、
  管理ポイント名を指定した場合は 条件→表側→表頭 の順に探索、未指定時は
  時間フィールドの時間型管理ポイント（NaviGetControlPointForTimeSpan）を自動選択します。
- 設定は対象ファイル設定モーダルの「基本・入出力」タブ内「抽出期間（動的日付）」で行います。
  ・期間の単位: 月度（YYYYMM00 / NAVI_MONTH）または 年月日（YYYYMMDD / NAVI_YMD）
  ・開始期(S)・終了期(E): 当月／当日を基準に、前後Nを指定（SymfoNaviの相対指定と同じ考え方）
  ・よく使う組み合わせ: 今月度／前月度／前月〜今月／当日／前日／過去7日／前日〜当日 をワンクリック適用
  ・対象の時間管理ポイント: 空欄で自動、または「候補を取得」でRNE内の時間型を自動検出して選択
- プレビューは処理日時を基準に実際の抽出範囲を即時表示します（例: 2026年6月度 ～ 2026年7月度）。
- 期間が有効なジョブでは実行ログに STEP phase=api_change_period と DYNAMIC_PERIOD を記録し、
  適用した単位・開始終了(YYYYMMDD/YYYYMM00)・対象管理ポイントを後から追跡できます。
- 注意: 相対期間が有効なのに時間型管理ポイントの特定や期間適用に失敗した場合は、
  誤った期間での公開を避けるためジョブを失敗として扱います（RNEの設定で全期間抽出することはしません）。
- DDE互換方式では本機能は適用されません（Navigator API方式で使用してください）。
- 候補の自動検出は NaviGetControlPointNumber / NaviGetControlPoint2 / NaviGetControlPointType /
  NaviGetNameCP を使用します。DLLがこれらを公開していない環境では手入力または自動選択で動作します。
