# デスクトップ版（Tauri / Rust / Python）への移行の検証

いまの形（Flask が 127.0.0.1:5031 で待ち受け、ブラウザで開く）から、Defect-Pitch-Analyzer（DPA）の版 2.0.0 と同じ形
（Tauri の窓＋Python を標準入出力でつなぐ・ポートなし）へ移せるかを、**実装に入る前に**確かめた記録。
この文書は「何を移せるか・どこへ移すか・何で確かめたか・何が分からないか・どう進めるか」を残す。

- 検証のときの試作は、第1段階（1.95.0）で本番の `desktop/`（窓）と `sidecar.py`（窓口）になった（§10）。評価は `tests/` と `desktop/selftest_runner.py`。
- 第2段階（1.96.0）でブラウザ版の起動の仕組みを外し、入口を `DataRelay.exe` だけにした。main に入ると Release に配る zip を置く（§11）。
- 結果（2026-10-02）: **全92ルートと、ルート以外の仕組みのすべてに移行先があり、移せないと分かった機能は無い。**
  ポートなしの窓口は全ルートで今と同じ答えを返し（Linux・Windows）、Tauri の試作は常駐・保存・ファイル選択・終わり方を
  本物の WebView2 の中で確かめた。ただし社内の PC・本物の Navigator サーバーと Access でしか確かめられない項目が残る（§7）。

---

## 1. 移す理由 ―― ポートとブラウザが起こしていたこと

| 起きたこと | それを抑えるために足した仕組み |
|---|---|
| ランチャーが自分自身（127.0.0.1:5031）への確認を社内プロキシへ送って失敗し、動いているサーバーを起動 40 秒後に止めていた（1.92.1） | ランチャー・本体・停止ツールのプロキシを通さない問い合わせ、待ち受けの直接確認 |
| 心拍（ブラウザからの生存信号）がスリープ・裏のタブの凍結で止まり、待機しているだけでサーバーが落ちた（1.90.1） | 「閉じた」という明示の知らせだけで終える決まり、閉じた記録の期限と掃除 |
| タブを閉じたかどうかをサーバーが知る手段が無い | 心拍・`pagehide` の知らせ・猶予・監視スレッド（`heartbeat_watchdog`） |
| 答えなくなったのか落ちたのかが分からない | 自分自身への HTTP の確認（`self_probe`）とスレッドの書き出し |
| 古いサーバーがポートを掴んで残る・ほかのプログラムがポートを使っている | `launch_guard.py`・`stop_app.bat`・`process_manager.py`・起動前のポート確認 |
| 起動を待つ画面がポートを推し量る | `loading.html`・`start.vbs`（574 行）の起動確認 |
| 「終了」を押してもタブはブラウザが閉じさせない | 終わり方の選択（1.77.0）・閉じられないときの案内 |

どれも「ポートを開いて、別のプログラム（ブラウザ）から問い合わせる」ことから来ている。デスクトップ版ではポートそのものを無くし、
窓を閉じたことは窓（Rust）が直接受け取る。**ハートビートは要らなくなる**（利用者の判断どおり）。

一方で **常駐（タスクバーの通知領域に入れて、自動実行をバックグラウンドで続ける）は必要な機能として残す**。
いまは心拍を引き金にしているが、機能としては心拍と別物で、デスクトップ版では「× を押したときに Rust が Python へ理由を聞く」形になる（§3・検証2で確認）。

## 2. 役割の分け方（得意な分野ごと）

| 受け持つもの | 何を | 理由 |
|---|---|---|
| **Rust**（Tauri の exe） | 窓・通知領域のアイコン・常駐（隠す・出し直す）・1つだけ起動・起動と終了・静的ファイル（HTML・JS・CSS）・ファイル/フォルダーの選択・保存ダイアログ・エクスプローラーで開く・中身（Python）の監督と起こし直し | OS の窓・プロセス・ファイルを直接扱える。止まらない・残らないことを型と所有で保証しやすい。いまは pywin32・tkinter・VBScript・バッチに分かれている仕事が1か所にまとまる |
| **Python**（いまの `app.py`・`lib/`） | 業務の処理のすべて ―― Navigator API（SymNaviA.dll・ワーカーで隔離）・DDE・ACCESS（COM）・出力と公開・分割・読取/結合マスタ・スケジューラー・設定DBの同期・常駐の理由の判定 | 試験と実運用で固めた処理。DLL（ctypes）・DDE・COM（pywin32）は Python に実績がある。書き直す利点より危うさが大きい |
| **画面**（WebView2） | いまの HTML/JS/CSS | 変えない。問い合わせは `fetch('/api/...')` のまま。心拍まわりだけ外す |

Flask は**残すが、サーバーとしては使わない**。URL の振り分けと答えの組み立て（WSGI）として、窓口がプロセスの中で直接呼ぶ。
92 本のルートの書き方・試験はそのまま使える。

## 3. つなぎ方（ポートなし）

```
 WebView2（画面）
   │ fetch("/api/...")  … 置き場は http://datarelay.localhost/（Windows）・datarelay://localhost/（ほか）
   ▼
 Rust: 自前の仕組み "datarelay" を受ける（router.rs）
   ├─ /・/static/…                → ディスクから直接（Python の起動を待たずに画面が出る）
   ├─ /api/pick-file・pick-folder  → 窓のダイアログ（いまの tkinter）
   ├─ /api/open-path               → 窓が開く（いまの os.startfile）
   ├─ 答えが「保存してください」   → 窓の保存ダイアログで受けて書く（画面へは 204）
   └─ それ以外                     → 中身へ渡す
                                      │ 標準入出力の枠（frame.rs ⇄ sidecar.py。DPA と同じ形）
                                      ▼
                                Python: Flask のアプリを WSGI のまま呼ぶ（いまと同じ答え）
                                      └─ 抽出ワーカー（api_worker.py）は子プロセス（いまと同じ）

 × を押す → Rust が Python に「常駐を続ける理由」（実行中・キュー・自動実行の予定・影実行）を聞く
            ├─ 理由あり → 窓を隠し、通知領域に残る（Python はそのまま自動実行を続ける）
            └─ 理由なし → 終わる（Rust が Python の入力を閉じる → Python は自分で終わる）
```

- **枠**: ヘッダー JSON 1行（`len` が本文のバイト数）＋本文そのまま。base64 にしないので ZIP・EXCEL・大きな一覧でも膨らまない。
- **標準出力の保護**: 窓口は fd 1 を標準エラーへ向け直す。本体・抽出ワーカーが `print` しても枠に混ざらない（検証1で確認）。
- **終わり方**: Rust が強制終了されても OS がパイプを閉じるので、Python は入力の終わりを見て自分で終わる。心拍で推し量る必要が無い。
- **1つだけ起動**: 2つめの exe は前の窓を前に出して終わる（常駐で隠れていても出す）。ポートを見て止め直す仕組みが要らない。

評価の途中で、評価そのものの誤りを4つ見つけて直した（どれも窓口の違いではなかった。4つめは §5.1）:

1. ログの件数が 1 行違った → ルートの一覧を取る補助のプロセスが、片方の置き場に終了時のログを書いていた。補助には別の置き場を使わせた。
2. 裏で走る調べものの数・ログの本文が違った → 直前に起こしたスレッドが終わったかどうかの違い。聞く前に両方の裏が落ち着くのを待つ形にし、
   ログは pid・ミリ秒・スレッドの行の順序を除いた「何の記録が何件か」で比べた。
3. 子プロセスの print の試験が、子を窓口の中でなく評価の側から起こしていて何も確かめていなかった → 窓口の中から起こす試験だけを残した。

揃えて比べた値は「その時刻・その置き場・そのプロセスでしか決まらないもの」だけ（時刻・pid・作業フォルダー・取り込みで振られる uuid・実行キューの番号）。

速さ（参考・Linux の WebKitGTK・1回の問い合わせの平均）: Python が答える API 約 1.2ms、Rust が返す部品 約 2.5ms。どちらも数 ms で、操作で分かる差ではない。

### 5.1 Windows（WebView2）の結果

`.github/workflows/desktop-poc.yml`（windows-latest・Python 3.12 64bit・Rust 1.99・WebView2 は Edge 153）。2026-10-02 の実行で**すべての手順が合格**。

| 手順 | 結果 |
|---|---|
| Python の試験（`tests/` 全部。検証1の全ルートの突き合わせを含む） | 合格 |
| `cargo test --locked`・`cargo build --release --locked` | 合格 |
| 自己診断（本物の WebView2・ポートなし・**pythonw で窓なし**） | **18 項目すべて合格**。速さは Python の API 5.3ms・Rust の部品 7.5ms（CI の機械はばらつきが大きく、どちらが速いとは言えない。どちらも数 ms） |
| 自己診断（閉じるだけの型） | 理由が無いまま × → **2.7 秒で終了コード 0、Python は残らない** |

Windows で初めて分かったこと:

- 1回目と2回目の実行は、検証1の `/api/log` の1行だけが不一致で止まった。違っていたのは、Navigator API の診断に起こした子プロセスの
  番号（`pid=7288` と `pid=1588`）。DLL を実際に読みに行く Windows でだけ出る行で、評価が揃えていたのは記録の頭の `[pid 3093]` の形だけだった。
  窓口の違いではなく評価の揃え方の漏れで、`pid=` の形も揃えるように直した（番号以外が違えば不一致になることも試験で確かめる）。
- CI の機械には Navigator の依存 DLL が無いので、同梱の `SymNaviA.dll`（64bit）は読み込みに失敗する。そのとき**窓口の中から起こした診断の子プロセスが
  理由を返して終わり、アプリ（窓口）は動き続けた**（`API_DIAG_WORKER returncode=2` のあとも答え続けている）。1.92.0 で入れた「DLL を本体から追い出す」隔離が、
  デスクトップ版の形でもそのまま効いている。

## 7. 分からないこと・実機で確かめること

ここに挙げたものは、この環境（Linux）と GitHub Actions の Windows 機では確かめられない。

| 項目 | 何が分からないか | 確かめ方 |
|---|---|---|
| 署名の無い exe | 社内の PC で SmartScreen・AppLocker に止められないか。**特に共有フォルダー（BOX）上の exe を直接起動したとき**に警告が出るか。**分からない** | 実機で exe を置いて起動する。止められるなら、exe だけ手元（%LOCALAPPDATA%）に置き、中身は共有を読む形にする |
| WebView2 の実行環境 | Windows 11 には標準で入っている。入っていない PC では窓が開かない。**社内の PC の状態は分からない** | 実機で起動する |
| Navigator API・DDE・ACCESS | 呼び出し方は変わらないが、親が launch_guard から exe に変わる。環境変数・作業フォルダー・窓なし（CREATE_NO_WINDOW）が同じに引き継がれるかを、**本物の Navigator サーバーと Access で**確かめる必要がある | 実機で RNE を1本（API）・1本（DDE）・ACCESS 出力を1本、デスクトップ版から流す |
| 実際のダイアログ・通知 | 自己診断ではダイアログを出せない（押す人がいない）ので、決めた場所へ保存して確かめた。本物のダイアログの見た目・初期フォルダー・ファイルの種類の絞り込みは**確かめていない** | 実機で操作する |
| 常駐中の通知（バルーン） | いまは pywin32 で「常駐しています」と知らせている。Tauri の通知（tauri-plugin-notification）は試作に入れていない | 実装のときに足して実機で見る |
| 夜間の自動実行 | 窓を隠したまま数時間〜一晩、スケジューラーが動き続けるか（スリープ復帰を含む） | 実機で一晩置く |

## 8. 進め方（段階）

**第1段階: 窓口と窓（業務の処理は1行も変えない）**
1. 窓口（`sidecar.py`）を直下に置く。起動して裏で始めること（スケジューラー・実行の受け付け・作業フォルダーの掃除・設定の移行）を
   `app.py` の `__main__` から1つの関数へ切り出し、ブラウザ版と窓口の両方から呼ぶ（DPA の `boot.py` と同じ）。
2. Rust の exe を `desktop/` に置く（試作を土台にする）。Python の探し方は `start.vbs` と同じにする（DPA の `locate.rs`）。
3. **DPA と違うところ**: 中身（Python）が止まったら、**次の問い合わせを待たずにすぐ起こし直す**。
   DataRelay ではスケジューラーが Python の中にあり、窓を隠して常駐しているあいだは問い合わせが来ない ―― DPA と同じ
   「次の問い合わせで起こし直す」では、常駐中に止まると自動実行が朝まで止まったままになる。
4. 終了は「Python が後始末（キューを空に・実行中なら中断・ワーカーと非表示の SymfoNavi を止める・設定を書き出す）して
   答える → Rust が終える」にする。いまの `shutdown_app`・`request_shutdown_from_tray` の後始末をそのまま使い、`os._exit` だけ外す。
   （試作の「終了」は入力を閉じるだけで、この後始末を呼んでいない。）
5. 常駐の理由は専用の問い合わせにする（試作は既存の `/api/heartbeat-status` の一部を読んだ）。
6. 移行の間は**両方を配る**（DPA と同じ）。デスクトップ版で困らないことが実機で確かめられてから第2段階へ。

**第2段階: 起動の仕組みを外す**（1.96.0 で実装。§11）
- §6 のものを外す。画面から心拍・閉じる知らせ・接続が切れた表示を外す。
- 当初は「デスクトップ版で困らないことが実機で確かめられてから」としていたが、利用者の判断で先に進めた。§7 の実機の確認は残っている（§11 の「残っていること」）。

**第3段階: Rust へ移す候補（同じ入力で同じ答えになることを試験で示せるときだけ）**

| 候補 | 利点 | 気をつけること |
|---|---|---|
| 中間 CSV の解析と XLSX・CSV の書き出し | 6 万行×178 列で解析 2.84 秒（実測）。Rust なら数分の1になる見込み。メモリも減る | 文字コードの判定順・桁数の過不足の扱い・集計表の見出しの畳み方（`navi_crosstab`）を同じにする。いまの試験（`test_crosstab.py` の評価）で突き合わせる |
| 公開（共有フォルダーへの安全な差し替え・保留の適用・世代の控え） | ファイルの扱いは Rust が得意。使用中のときの待ちと再試行を型で書ける | 共有が遅いとき・使用中のときの扱いを変えない |
| 共有のファイルを手元へ写してから読む（`navi_localcopy`） | 同上 | 写しの置き場・上限を変えない |

移さないもの: Navigator API の呼び出し（ctypes・ワーカーでの隔離。DLL の文字列の受け渡しは `[要確認]` のまま Rust から呼ぶ利点が無い）、
DDE・ACCESS（pywin32）、分割の設計・読取/結合マスタ・スケジュールの規則（試験と実運用で固めた業務の処理で、Python のままで遅くない）。

## 9. 作り方・配り方の変化

- **作る**: `cargo build --release`（Windows では Rust と Visual Studio の C++ ビルドツールが要る）。CI（Windows）が作って自己診断する。
  main に入ったものは Release（`v{版}`）に `DataRelay.zip`（フォルダー一式＋exe）と `DataRelay.exe` を置く（1.96.0・§11）。
- **置く**: `DataRelay.exe` を `app.py` のフォルダーに置く（exe は自分の場所から上へたどって `app.py` を探す）。共有上の exe が止められるなら §7 のとおり手元に置く。
- **Python**: いまと同じ（各 PC に Python と `config/requirements.txt` の部品）。部品が無ければ exe が初回に `pip install --user` する（1.96.0。start.vbs の役目）。増える要件は WebView2 だけ。Python を同梱する（embeddable）かは別に決める。
- **中身の更新**: Python の部分はいまと同じく共有のファイルを置き換える。exe は動いている間は上書きできない（Windows の決まり）ので、exe の更新は全員が閉じてから。

## 10. 第1段階の実装（1.95.0）

§8 の第1段階を実装した。業務の処理（抽出・出力・分割・マスタ・スケジュールの規則）は1行も変えていない。

| もの | 中身 |
|---|---|
| `sidecar.py` | 窓口（検証1の試作を本番に）。`app.boot_app('desktop')` で裏の処理を起こしてから「準備できた」を知らせる |
| `app.py` の `boot_app(mode)` | 起動して裏で始めることを1か所に切り出した。ブラウザ版（`__main__`）とデスクトップ版の両方が呼ぶ。心拍の監視・自分への疎通確認・pywin32 の常駐アイコンはブラウザ版だけ |
| `app.py` の `prepare_exit` | 終わる前の後始末（キュー・中断・ワーカーと非表示の SymfoNavi・設定の書き出し）を1つにまとめた。画面の「終了」・通知領域の「終了」・デスクトップ版の窓の「終了」が同じものを使う |
| `/api/residency`・`/api/app-cleanup` | 常駐を続ける理由／os._exit しない後始末。デスクトップ版の窓が使う |
| `lib/navi_instance.py` | 中身を利用者ごとに1つにする錠（下の「実装で分かったこと」1） |
| `desktop/` | 窓（検証2の試作を本番に）。起動画面・Python の探し方（`locate.rs`）・止まったらすぐ起こし直す監督・終了時の後始末・常駐の通知・窓の記録（`desktop.log`）・`/` と静的ファイル |
| `static/app.js` | デスクトップ版では心拍・閉じる知らせ・閉じるときの確認を出さない。「終了」「タスクバーへ」は窓に任せる |
| `desktop/selftest_runner.py`・`.github/workflows/desktop.yml` | 自己診断の3つの型（全体・閉じるだけ・起こし直し）を、手元（Linux）と CI（Windows）で同じ物差しで流す |

実装で分かったこと（検証では見えていなかったもの）:

1. **ブラウザ版とデスクトップ版を同時に起こすと、自動実行が二重に走る**。移行の間は両方を配るのに、スケジューラーを持つ中身が2つ動いてしまう
   （DPA にはスケジューラーが無いので起きなかった）。`boot_app` の最初に OS のファイルロック（利用者ごと）を取り、取れなければ起動しない。
   ブラウザ版はログに残して止まり、デスクトップ版は起動画面に「ブラウザ版がすでに動いています（pid・いつから）」と出す。プロセスが落ちても OS が錠を外す（`tests/test_instance.py`）。
2. **× で終わったあと、中身（Python）がときどき残った**（2回に1回）。原因は2つの重なり: (a) 窓の終わり方が中身の値を「捨てる」だけで、
   ほかの糸が値を持っていると入力を閉じる・待つ・止めるが走らなかった (b) 中身は入力が閉じたあとの設定の書き出しに上限が無く、そこで止まると誰も止めない。
   窓は値の持ち主に関わらず必ず「入力を閉じる → 3 秒待つ → 止める」を行い、中身は書き出しを 3 秒で打ち切るようにした。直したあと、閉じるだけの型を 10 回続けて流して 10 回とも合格。
3. **起こし直しは、見張りより先に画面の問い合わせが起こすことがある**（どちらが先でも結果は同じ）。どの道で起こしても窓の記録に残るよう、起こすたびに記録する形にした。

評価（2026-10-02・Linux）: Python の試験 40 件・`cargo test` 11 件・自己診断（全体 24 項目・閉じるだけ 4 項目・起こし直し 6 項目）すべて合格。ブラウザ版の起動・終了も確かめた。
Windows（WebView2）は `.github/workflows/desktop.yml` で同じものを回す。

§7 の「実機で確かめること」はそのまま残っている（社内 PC の署名なし exe・本物の Navigator サーバーと Access・一晩の常駐）。

## 11. 第2段階の実装（1.96.0）

§8 の第2段階を実装した。業務の処理（抽出・出力・分割・マスタ・スケジュールの規則）は1行も変えていない。

| 外したもの | 引き継いだ先 |
|---|---|
| `start.vbs`・`start.bat`（Python を探す・Flask が無ければ pip で入れる） | 窓の `locate.rs`（Flask を読める Python を選ぶ。無ければ起動画面を出したまま `pip install --user -r config\requirements.txt` して探し直す） |
| `start_app.py`・`lib/launch_guard.py`（作業場所の準備・多重起動の防止・起動待ち）・`loading.html` | 窓（1つだけ起動・起動画面）と `sidecar.py`（作業場所）。中身を1つにする錠（`navi_instance`）は残した ―― 古い版のフォルダーに残ったブラウザ版から起こされた中身も止めるため |
| `stop_app.bat`・`lib/process_manager.py` | 画面の「終了」・通知領域の「終了」（窓が後始末を頼んでから終わる） |
| `lib/tray_icon.py`（pywin32 の通知領域・知らせのバルーン） | 窓の通知領域。**知らせ（抽出の失敗など）の通知**は窓が `/api/alerts` を 5 秒ごとに見て出す |
| app.py の心拍の監視・自分への疎通確認・常駐の出入り・ポートでの起動 | 窓（× を受け取る・中身を見張って起こし直す）。常駐の理由の判定（`residency_reason`）は Python に残した |
| 受け口 `/api/heartbeat`・`/api/heartbeat-status`・`/api/browser-closing` | 外した。画面の「アプリ監視」は窓の `/api/desktop-status`（中身の pid・Python・起こし直しの回数）を見る |
| 受け口 `/api/shutdown-app`・`/api/stay-resident`・`/api/pick-file`・`/api/pick-folder`・`/api/open-path`・`GET /` | 窓が受け持つので、中身からは外した（呼ばれない tkinter・os._exit を残さない） |
| 画面のブラウザ版の分岐（心拍・閉じる知らせ・タブを閉じる工夫・閉じる前の確認・常駐の案内） | 外した。画面はデスクトップ版だけの形 |

実装で分かったこと（1.95.0 のデスクトップ版に潜んでいた不具合）:

1. **窓の「エクスプローラーで開く」「ファイル選択」が相対パス・`<PC>` を直していなかった**。設定のパスはアプリフォルダー基準の相対（`.\output`）や `<PC>` のことがあり、
   窓の作業フォルダー基準で読まれて「出力先が見つかりません」・初期フォルダーが効かない、になっていた（ブラウザ版は Python の `resolve_path` を通していた）。
   自己診断がダイアログを出せないため、パスを直す前に答えを返していて見逃していた。窓は `/api/path-convert` に聞いて直す（決まりは `resolve_path` だけが持つ）。
   自己診断に相対パス・`<PC>` を渡す項目を足し、直す前は3項目とも不合格になることを確かめてから直した。
2. **知らせの Windows 通知が出ていなかった**。`add_alert` は pywin32 の通知領域アイコン経由で通知していたが、デスクトップ版ではそのアイコンを起こさない。窓が出す形にした。
3. **Python が複数ある PC で Flask の無い方を選ぶことがあった**（1.95.0 の Windows の CI で見つけて直した。`py -3` が最新版を指すため）。

配り方（`.github/workflows/desktop.yml` の `release`）:

- main に入るたびに、Windows で試験・exe・自己診断を通したものだけを Release `v{版}` に置く。`DataRelay.zip`（`git archive` ＋ exe）と `DataRelay.exe`。
- zip に入れないもの（試験・exe の作り方・移行の記録・見本・CI）は `.gitattributes` の `export-ignore` にだけ書く。`tests/test_package.py` が、起動に要るものが入り、入れないものが入らないことを見る。
- ファイル名に版を入れない（最新版の取り先 `releases/latest/download/DataRelay.zip` をいつも同じにするため）。版を上げずに main が進んだら、その版の Release をタグごと作り直す（配る zip とタグの指すコミットを食い違わせない）。
- exe・中身・更新履歴の版の数字が揃っていることも試験で見る（Release のタグは中身の版で付ける）。

評価（2026-10-02・Linux）: Python の試験 50 件・`cargo test` 14 件・自己診断（全体 25 項目・閉じるだけ 4 項目・起こし直し 7 項目）すべて合格。
移行先の表の試験（`tests/test_route_plan.py`）は、中身の URL 表と窓の振り分けの両方と突き合わせる形にした。外す前の中身に当てると、外すべきルートと窓へ移したのに残るルートで落ちる。
Flask の無い Python だけの状態から、窓が部品を入れて起動し、自己診断が全部合格することも確かめた。

残っていること: §7 の実機の確認（社内 PC での署名の無い exe・本物の Navigator サーバーと Access・一晩の常駐）。
ブラウザ版という逃げ道は無くなったので、署名の無い exe が社内の PC で止められる場合は、§7 のとおり exe だけを手元（%LOCALAPPDATA%）に置く形を先に用意する必要がある。
