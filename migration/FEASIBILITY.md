# デスクトップ版（Tauri / Rust / Python）への移行の検証

いまの形（Flask が 127.0.0.1:5031 で待ち受け、ブラウザで開く）から、Defect-Pitch-Analyzer（DPA）の版 2.0.0 と同じ形
（Tauri の窓＋Python を標準入出力でつなぐ・ポートなし）へ移せるかを、**実装に入る前に**確かめた記録。
この文書は「何を移せるか・どこへ移すか・何で確かめたか・何が分からないか・どう進めるか」を残す。

- 試作と評価はすべて `migration/` と `tests/` にあり、**実行の経路には一切入らない**（いまのアプリの動きは変わらない）。
- 結果（2026-10-02）: **全92ルートと、ルート以外の仕組みのすべてに移行先があり、移せないと分かった機能は無い。**
  ただし Windows の実機でしか確かめられない項目が残る（§7）。

---

## 1. 移す理由 ―― ポートとブラウザが起こしていたこと

| 起きたこと | それを抑えるために足した仕組み |
|---|---|
| ランチャーが自分自身（127.0.0.1:5031）への確認を社内プロキシへ送って失敗し、動いているサーバーを起動 40 秒後に止めていた（1.92.1） | ランチャー・本体・停止ツールのプロキシを通さない問い合わせ、待ち受けの直接確認 |
| 心拍（ブラウザからの生存信号）がスリープ・裏のタブの凍結で止まり、待機しているだけでサーバーが落ちた（1.90.1） | 「閉じた」という明示の知らせだけで終える決まり、閉じた記録の期限と掃除 |
| タブを閉じたかどうかをサーバーが知る手段が無い | 心拍・`pagehide` の知らせ・猶予・監視スレッド（`heartbeat_watchdog`） |
| 答えなくなったのか落ちたのかが分からない | 自分自身への HTTP の確認（`self_probe`）とスレッドの書き出し |
| 古いサーバーがポートを掴んで残る・ほかのプログラムがポートを使っている | `launch_guard.py`・`stop_app.bat`・`process_manager.py`・起動前のポート確認 |
| 起動を待つ画面がポートを推し量る | `loading.html`・`start.vbs`（574 行）の起動確認 |
| 「終了」を押してもタブはブラウザが閉じさせない | 終わり方の選択（1.77.0）・閉じられないときの案内 |

どれも「ポートを開いて、別のプログラム（ブラウザ）から問い合わせる」ことから来ている。デスクトップ版ではポートそのものを無くし、
窓を閉じたことは窓（Rust）が直接受け取る。**ハートビートは要らなくなる**（利用者の判断どおり）。

一方で **常駐（タスクバーの通知領域に入れて、自動実行をバックグラウンドで続ける）は必要な機能として残す**。
いまは心拍を引き金にしているが、機能としては心拍と別物で、デスクトップ版では「× を押したときに Rust が Python へ理由を聞く」形になる（§3・検証2で確認）。

## 2. 役割の分け方（得意な分野ごと）

| 受け持つもの | 何を | 理由 |
|---|---|---|
| **Rust**（Tauri の exe） | 窓・通知領域のアイコン・常駐（隠す・出し直す）・1つだけ起動・起動と終了・静的ファイル（HTML・JS・CSS）・ファイル/フォルダーの選択・保存ダイアログ・エクスプローラーで開く・中身（Python）の監督と起こし直し | OS の窓・プロセス・ファイルを直接扱える。止まらない・残らないことを型と所有で保証しやすい。いまは pywin32・tkinter・VBScript・バッチに分かれている仕事が1か所にまとまる |
| **Python**（いまの `app.py`・`lib/`） | 業務の処理のすべて ―― Navigator API（SymNaviA.dll・ワーカーで隔離）・DDE・ACCESS（COM）・出力と公開・分割・読取/結合マスタ・スケジューラー・設定DBの同期・常駐の理由の判定 | 試験と実運用で固めた処理。DLL（ctypes）・DDE・COM（pywin32）は Python に実績がある。書き直す利点より危うさが大きい |
| **画面**（WebView2） | いまの HTML/JS/CSS | 変えない。問い合わせは `fetch('/api/...')` のまま。心拍まわりだけ外す |

Flask は**残すが、サーバーとしては使わない**。URL の振り分けと答えの組み立て（WSGI）として、窓口がプロセスの中で直接呼ぶ。
92 本のルートの書き方・試験はそのまま使える。

## 3. つなぎ方（ポートなし）

```
 WebView2（画面）
   │ fetch("/api/...")  … 置き場は http://datarelay.localhost/（Windows）・datarelay://localhost/（ほか）
   ▼
 Rust: 自前の仕組み "datarelay" を受ける（router.rs）
   ├─ /・/static/…                → ディスクから直接（Python の起動を待たずに画面が出る）
   ├─ /api/pick-file・pick-folder  → 窓のダイアログ（いまの tkinter）
   ├─ /api/open-path               → 窓が開く（いまの os.startfile）
   ├─ 答えが「保存してください」   → 窓の保存ダイアログで受けて書く（画面へは 204）
   └─ それ以外                     → 中身へ渡す
                                      │ 標準入出力の枠（frame.rs ⇄ sidecar.py。DPA と同じ形）
                                      ▼
                                Python: Flask のアプリを WSGI のまま呼ぶ（いまと同じ答え）
                                      └─ 抽出ワーカー（api_worker.py）は子プロセス（いまと同じ）

 × を押す → Rust が Python に「常駐を続ける理由」（実行中・キュー・自動実行の予定・影実行）を聞く
            ├─ 理由あり → 窓を隠し、通知領域に残る（Python はそのまま自動実行を続ける）
            └─ 理由なし → 終わる（Rust が Python の入力を閉じる → Python は自分で終わる）
```

- **枠**: ヘッダー JSON 1行（`len` が本文のバイト数）＋本文そのまま。base64 にしないので ZIP・EXCEL・大きな一覧でも膨らまない。
- **標準出力の保護**: 窓口は fd 1 を標準エラーへ向け直す。本体・抽出ワーカーが `print` しても枠に混ざらない（検証1で確認）。
- **終わり方**: Rust が強制終了されても OS がパイプを閉じるので、Python は入力の終わりを見て自分で終わる。心拍で推し量る必要が無い。
- **1つだけ起動**: 2つめの exe は前の窓を前に出して終わる（常駐で隠れていても出す）。ポートを見て止め直す仕組みが要らない。

評価の途中で、評価そのものの誤りを3つ見つけて直した（窓口の違いではなかった）:

1. ログの件数が 1 行違った → ルートの一覧を取る補助のプロセスが、片方の置き場に終了時のログを書いていた。補助には別の置き場を使わせた。
2. 裏で走る調べものの数・ログの本文が違った → 直前に起こしたスレッドが終わったかどうかの違い。聞く前に両方の裏が落ち着くのを待つ形にし、
   ログは pid・ミリ秒・スレッドの行の順序を除いた「何の記録が何件か」で比べた。
3. 子プロセスの print の試験が、子を窓口の中でなく評価の側から起こしていて何も確かめていなかった → 窓口の中から起こす試験だけを残した。

揃えて比べた値は「その時刻・その置き場・そのプロセスでしか決まらないもの」だけ（時刻・pid・作業フォルダー・取り込みで振られる uuid・実行キューの番号）。

速さ（参考・Linux の WebKitGTK・1回の問い合わせの平均）: Python が答える API 約 1.2ms、Rust が返す部品 約 2.5ms。どちらも数 ms で、操作で分かる差ではない。

## 7. 分からないこと・実機で確かめること

ここに挙げたものは、この環境（Linux）と GitHub Actions の Windows 機では確かめられない。

| 項目 | 何が分からないか | 確かめ方 |
|---|---|---|
| 署名の無い exe | 社内の PC で SmartScreen・AppLocker に止められないか。**特に共有フォルダー（BOX）上の exe を直接起動したとき**に警告が出るか。**分からない** | 実機で exe を置いて起動する。止められるなら、exe だけ手元（%LOCALAPPDATA%）に置き、中身は共有を読む形にする |
| WebView2 の実行環境 | Windows 11 には標準で入っている。入っていない PC では窓が開かない。**社内の PC の状態は分からない** | 実機で起動する |
| Navigator API・DDE・ACCESS | 呼び出し方は変わらないが、親が launch_guard から exe に変わる。環境変数・作業フォルダー・窓なし（CREATE_NO_WINDOW）が同じに引き継がれるかを、**本物の Navigator サーバーと Access で**確かめる必要がある | 実機で RNE を1本（API）・1本（DDE）・ACCESS 出力を1本、デスクトップ版から流す |
| 実際のダイアログ・通知 | 自己診断ではダイアログを出せない（押す人がいない）ので、決めた場所へ保存して確かめた。本物のダイアログの見た目・初期フォルダー・ファイルの種類の絞り込みは**確かめていない** | 実機で操作する |
| 常駐中の通知（バルーン） | いまは pywin32 で「常駐しています」と知らせている。Tauri の通知（tauri-plugin-notification）は試作に入れていない | 実装のときに足して実機で見る |
| 夜間の自動実行 | 窓を隠したまま数時間〜一晩、スケジューラーが動き続けるか（スリープ復帰を含む） | 実機で一晩置く |

## 8. 進め方（段階）

**第1段階: 窓口と窓（業務の処理は1行も変えない）**
1. 窓口（`sidecar.py`）を直下に置く。起動して裏で始めること（スケジューラー・実行の受け付け・作業フォルダーの掃除・設定の移行）を
   `app.py` の `__main__` から1つの関数へ切り出し、ブラウザ版と窓口の両方から呼ぶ（DPA の `boot.py` と同じ）。
2. Rust の exe を `desktop/` に置く（試作を土台にする）。Python の探し方は `start.vbs` と同じにする（DPA の `locate.rs`）。
3. **DPA と違うところ**: 中身（Python）が止まったら、**次の問い合わせを待たずにすぐ起こし直す**。
   DataRelay ではスケジューラーが Python の中にあり、窓を隠して常駐しているあいだは問い合わせが来ない ―― DPA と同じ
   「次の問い合わせで起こし直す」では、常駐中に止まると自動実行が朝まで止まったままになる。
4. 終了は「Python が後始末（キューを空に・実行中なら中断・ワーカーと非表示の SymfoNavi を止める・設定を書き出す）して
   答える → Rust が終える」にする。いまの `shutdown_app`・`request_shutdown_from_tray` の後始末をそのまま使い、`os._exit` だけ外す。
   （試作の「終了」は入力を閉じるだけで、この後始末を呼んでいない。）
5. 常駐の理由は専用の問い合わせにする（試作は既存の `/api/heartbeat-status` の一部を読んだ）。
6. 移行の間は**両方を配る**（DPA と同じ）。デスクトップ版で困らないことが実機で確かめられてから第2段階へ。

**第2段階: 起動の仕組みを外す**
- §6 のものを外す。画面から心拍・閉じる知らせ・接続が切れた表示を外す。

**第3段階: Rust へ移す候補（同じ入力で同じ答えになることを試験で示せるときだけ）**

| 候補 | 利点 | 気をつけること |
|---|---|---|
| 中間 CSV の解析と XLSX・CSV の書き出し | 6 万行×178 列で解析 2.84 秒（実測）。Rust なら数分の1になる見込み。メモリも減る | 文字コードの判定順・桁数の過不足の扱い・集計表の見出しの畳み方（`navi_crosstab`）を同じにする。いまの試験（`test_crosstab.py` の評価）で突き合わせる |
| 公開（共有フォルダーへの安全な差し替え・保留の適用・世代の控え） | ファイルの扱いは Rust が得意。使用中のときの待ちと再試行を型で書ける | 共有が遅いとき・使用中のときの扱いを変えない |
| 共有のファイルを手元へ写してから読む（`navi_localcopy`） | 同上 | 写しの置き場・上限を変えない |

移さないもの: Navigator API の呼び出し（ctypes・ワーカーでの隔離。DLL の文字列の受け渡しは `[要確認]` のまま Rust から呼ぶ利点が無い）、
DDE・ACCESS（pywin32）、分割の設計・読取/結合マスタ・スケジュールの規則（試験と実運用で固めた業務の処理で、Python のままで遅くない）。

## 9. 作り方・配り方の変化

- **作る**: `cargo build --release`（Windows では Rust と Visual Studio の C++ ビルドツールが要る）。CI（Windows）が作って自己診断し、exe を Artifacts に置く（DPA と同じ）。
- **置く**: `DataRelay.exe` を `app.py` のフォルダーに置く（exe は自分の場所から上へたどって `app.py` を探す）。共有上の exe が止められるなら §7 のとおり手元に置く。
- **Python**: いまと同じ（各 PC に Python と `config/requirements.txt` の部品）。増える要件は WebView2 だけ。Python を同梱する（embeddable）かは別に決める。
- **中身の更新**: Python の部分はいまと同じく共有のファイルを置き換える。exe は動いている間は上書きできない（Windows の決まり）ので、exe の更新は全員が閉じてから。
